# Official BTC video ingestion

This isolated job reads the official Videos and Keyframes ZIP URLs listed in the AIC2026 submission sheet. It uses HTTP Range requests to inspect the video ZIP central directory and streams each original MP4 through `rclone rcat`; it never downloads a complete video ZIP or stores a local video. The official keyframe ZIP is streamed as one Drive file per logical batch, and the exact BTC timestamps are written as one JSONL file per batch. This avoids one Drive API upload per frame while preserving the original data losslessly. No semantic labels or frame extraction are performed.

The logical hierarchy under the AIC root is `01_Videos_Original/L21/L21_V001/L21_V001.mp4`, plus `01_Videos_Original/L21/timestamps_L21.jsonl` and `01_Videos_Original/L21/keyframes/keyframes_L21.zip`. L26 archive parts are kept under their logical batch folders (`L26_a` … `L26_e`); source archive/member names remain in each catalog. Keyframes are the exact BTC-supplied ZIP contents, never regenerated.

## One-time setup

1. Preferred for a personal My Drive: on a trusted machine, run `rclone config` and create a Google Drive remote named `drive` using your user OAuth login. Set its root folder to `1E8u-YURTRexdR1Ax4Hu2aq7Vt646VQuN` (or ensure the generated config contains `root_folder_id = 1E8u-YURTRexdR1Ax4Hu2aq7Vt646VQuN`). Copy the complete config file contents, then add them as the GitHub Actions secret `RCLONE_CONFIG_DRIVE` (Settings → Secrets and variables → Actions). Do not paste or commit the config/token anywhere else.
2. Fallback for a Shared Drive only: create a Google Cloud service account with Drive API access and download its JSON key, share the target Shared Drive/folder with its email as Content manager, and add the complete JSON as `GDRIVE_SERVICE_ACCOUNT_JSON`. Service accounts cannot upload to a personal My Drive after their storage quota is exhausted.
3. For a smoke test, run `Upload official videos to Drive` manually for one logical batch. For the complete database, run `Upload full official database sequentially`; its 14 jobs are constrained to one active batch at a time. Each batch uploads all videos individually (so they can be previewed in Drive), then one official keyframe ZIP and one timestamp JSONL. The workflow uses the AIC root ID `1E8u-YURTRexdR1Ax4Hu2aq7Vt646VQuN` and fetches the exact timestamp map to runner temporary storage before ingestion.

The uploader applies conservative Google Drive pacing (one transfer, one checker, one request per second, 10-second Drive pacer sleep, and 256 MiB resumable chunks). The full-database workflow runs batches sequentially to avoid project rate limits. A failed batch can be rerun after the API quota cools down; video paths are deterministic and the official archive uploads are reproducible.

The workflow refuses to run without one of the two secrets. With OAuth, share the parent `AIC2026_VideoRAG` folder (ID `1E8u-YURTRexdR1Ax4Hu2aq7Vt646VQuN`) with the user who authorized rclone. With the service-account fallback, share it with the service-account email as Content manager. The job reads `02_Timelines/btc_keyframe_timestamps.jsonl` temporarily through rclone and writes exact batch JSONL indexes; it does not invent timestamps or YouTube chapters.
